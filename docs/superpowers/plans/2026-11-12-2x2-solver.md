# 2x2 Cube Solver Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Statische Web-App, die einen per Netz eingegebenen 2x2-Würfel optimal löst und die Lösung schrittweise zeigt; Deployment via GitHub Pages.

**Architecture:** Reines Modell (`cube.js`: Ecken-Zustand, Züge U/R/F, Facelets ↔ Zustand, Validierung), Solver (`solver.js`: BFS-Distanztabelle über 7!·3⁶ Zustände, gierige Descent-Lösung), austauschbare Ansicht (`views/net-view.js`) und UI-Steuerung (`app.js`).

**Tech Stack:** HTML/CSS/JS (ES-Module, kein Build), Tests mit `node --test` (Node ≥ 20), GitHub Actions + GitHub Pages.

**Spec:** `docs/superpowers/specs/2026-11-12-2x2-solver-design.md`

## Global Constraints

- Keine Laufzeit- und keine Dev-Abhängigkeiten; `package.json` nur mit `"type": "module"` und `"scripts": {"test": "node --test"}`.
- Ecke DBL bleibt fest; nur Züge U, R, F (je `X`, `X2`, `X'`) – 9 Züge.
- Lösung ist optimal (Half-Turn-Metrik), nie länger als 11 Züge.
- UI-Texte auf Deutsch.
- Modell und Solver ohne DOM-Zugriff (in Node testbar).
- `app.js` spricht Ansichten nur über `{ render(facelets), showMove(move, direction) }` an.

## Fixe Definitionen (gelten für alle Tasks)

**Facelet-Reihenfolge** (24 Einträge, je Seite zeilenweise, wie im Netz betrachtet):
`U 0-3, R 4-7, F 8-11, D 12-15, L 16-19, B 20-23`
- U (B oben): 0=UBL 1=UBR 2=UFL 3=UFR · R (U oben): 4=UFR 5=UBR 6=DFR 7=DBR
- F: 8=UFL 9=UFR 10=DFL 11=DFR · D (F oben): 12=DFL 13=DFR 14=DBL 15=DBR
- L: 16=UBL 17=UFL 18=DBL 19=DFL · B: 20=UBR 21=UBL 22=DBR 23=DBL

**Ecken** (Index: Name → Facelets im Uhrzeigersinn, beginnend mit U/D-Sticker):
`0 URF [3,4,9] · 1 UFL [2,8,17] · 2 ULB [0,16,21] · 3 UBR [1,20,5] · 4 DFR [13,11,6] · 5 DLF [12,19,10] · 6 DBL [14,23,18] · 7 DRB [15,7,22]`
Eckenfarben (Seitenbuchstaben) in derselben Reihenfolge: URF=[U,R,F], UFL=[U,F,L], ULB=[U,L,B], UBR=[U,B,R], DFR=[D,F,R], DLF=[D,L,F], DBL=[D,B,L], DRB=[D,R,B].

**Basiszüge** (cubie-Ebene, „replaced-by“): `new.cp[i] = s.cp[m.cp[i]]`, `new.co[i] = (s.co[m.cp[i]] + m.co[i]) % 3`
- U: cp=[3,0,1,2,4,5,6,7] co=[0,0,0,0,0,0,0,0]
- R: cp=[4,1,2,0,7,5,6,3] co=[2,0,0,1,1,0,0,2]
- F: cp=[1,5,2,3,0,4,6,7] co=[1,2,0,0,2,1,0,0]
`X2` = 2× X, `X'` = 3× X.

**Zustand → Facelets:** für Position i mit `c=cp[i]`, `o=co[i]`: `faces[cornerFacelets[i][(k+o)%3]] = cornerColors[c][k]` für k=0..2.

**Farben:** `W Y G B R O`; Gegenpaare W–Y, G–B, R–O. Standard-Gelöst (Default im UI): U=W, R=R, F=G, D=Y, L=O, B=B.

**Zug-Objekt:** `{ face: 'U'|'R'|'F', turns: 1 | 2 | -1 }`; Notation `R`, `R2`, `R'`.

## Review Focus

1. Gelöster Würfel in beliebiger Haltung (z. B. Gelb oben) → „Schon gelöst“, nicht Fehler. → Test in Task 2.
2. Spiegelverkehrte Ecke (richtige drei Farben, falsche Reihenfolge) → Fehlermeldung statt Fehllösung. → Test in Task 2.
3. Eingabe nach dem Lösen geändert → alte Lösung verschwindet (keine veraltete Schritt-Anzeige). → Prüfschritt in Task 4.
4. „Lösen“ vor Ende der Tabellenberechnung → Button deaktiviert. → Prüfschritt in Task 4.
5. Lösung aus Facelets (nicht nur aus Cubie-Zustand) angewandt ergibt einen einfarbigen Würfel pro Seite → Test in Task 3.

### Task 2: Facelets einlesen und validieren

**Files:**
- Modify: `src/cube.js`
- Test: `test/parse.test.js`

**Interfaces:**
- Consumes: `CORNER_FACELETS`, `CORNER_COLORS`, `toFacelets`, `applyMoves`, `parseMoves`, `SOLVED`
- Produces: `parseFacelets(facelets: (string|null)[24]) -> {ok:true, state, scheme} | {ok:false, error:string}`
  - `scheme` = `{U,R,F,D,L,B}` → Farbbuchstabe, so dass `toFacelets(state, scheme)` die Eingabe exakt reproduziert.
  - `COLOR_NAMES = {W:'Weiß',Y:'Gelb',G:'Grün',B:'Blau',R:'Rot',O:'Orange'}` exportiert.

Ablauf (Prüfungen in dieser Reihenfolge, erste Verletzung gewinnt; Fehlertexte exakt):
1. Feld leer → `"Es sind noch nicht alle Felder gefärbt."`
2. Farbe ≠ 4× → `"${Name} kommt ${n}× vor (erwartet: 4×)."` (erste Farbe in Reihenfolge W Y G B R O)
3. Schema aus DBL-Ecke: D=f[14], B=f[23], L=f[18]; U/F/R = Gegenfarben. Sind zwei davon Gegenfarben/gleich → wie 4.
4. Pro Position: drei Farben auf Seitenbuchstaben abbilden, passende Ecke c und Orientierung o mit `CORNER_COLORS[c][k] === sides[(k+o)%3]` suchen. Keine → `"Die Ecke mit ${A}/${B}/${C} gibt es auf einem Würfel nicht."` (Farbnamen in Facelet-Reihenfolge der Position)
5. Ecke doppelt → `"Eine Ecke kommt doppelt vor – bitte Eingabe prüfen."`
6. Summe co % 3 ≠ 0 → `"Eine Ecke ist verdreht – so ist der Würfel nicht lösbar."`

- [ ] **Step 1: Failing tests**
  - `round trip`: für 20 Zufallsmischungen (Länge 15): `parseFacelets(toFacelets(s))` → `ok`, `deepEqual(state, s)`
  - `solved in other orientation`: Facelets eines gelösten Würfels mit Schema `{U:'Y',D:'W',F:'B',B:'G',R:'R',L:'O'}` (Gelb oben, Blau vorne) → `ok && isSolved(state)`
  - `empty field`: ein `null` → Fehlertext 1
  - `color count`: Facelet 0 von `'W'` auf `'Y'` → `"Weiß kommt 3× vor (erwartet: 4×)."`
  - `mirrored corner`: in gelöster Eingabe Facelets 4 und 9 (URF: R- und F-Sticker) tauschen → Fehler beginnt mit `"Die Ecke mit"`
  - `twisted corner`: URF-Sticker [3,4,9] zyklisch rotieren → Fehlertext 6

### Task 3: Solver mit Distanztabelle

**Files:**
- Create: `src/solver.js`, `test/solver.test.js`

**Interfaces:**
- Consumes: `MOVES`, `applyMove`, `SOLVED`, `isSolved`
- Produces (`src/solver.js`):
  - `encode(state) -> number` = `permIndex * 729 + oriIndex`; permIndex = Lehmer-Code von `cp` ohne Position 6 (Werte 0..7 ohne 6, 0..5039); oriIndex = Basis-3 über `co[0..5]` (co[7] folgt aus Summe ≡ 0)
  - `decode(index) -> state`
  - `createSolver() -> { solve(state) -> Move[] , distance(state) -> number }` – baut einmalig Move-Tabellen (`Uint16Array` 5040×9, 729×9) und BFS-Distanz (`Uint8Array(3674160)`, 255 = unbesucht)
  - `solve`: solange Distanz > 0, ersten Zug aus `MOVES` wählen, dessen Folgezustand Distanz − 1 hat

- [ ] **Step 1: Failing tests** (Solver einmal pro Datei per `before` erzeugen)
  - `encode/decode round trip` für 50 Zufallszustände
  - `solved has distance 0 and empty solution`
  - `single move solved in one`: für jeden Zug in `MOVES` → Lösungslänge 1
  - `random scrambles`: 200 Mischungen (Länge 1–20): `isSolved(applyMoves(s, solve(s)))`, Länge ≤ Mischlänge, Länge ≤ 11
  - `max distance is 11`: Maximum der Tabelle === 11; Anzahl Einträge mit 255 === 0
  - `solves from facelets`: Zufallsmischung → `toFacelets` → `parseFacelets` → `solve` → `toFacelets(applyMoves(...), scheme)` hat pro Seite 4 gleiche Farben

Verhalten `app.js`:
- Startzustand: Default-Gelöst-Facelets; Palette (6 Farben, gewählte hervorgehoben); Klick färbt Feld.
- Buttons: „Lösen“, „Gelöst zurücksetzen“, „Leeren“; Schritt-Navigation: „⏮ Anfang“, „◀ Zurück“, „Weiter ▶“, „Ende ⏭“.
- Beim Laden: Status „Initialisiere Solver…“, „Lösen“ deaktiviert; Solver per `setTimeout(…, 0)` erzeugen, danach aktivieren.
- Lösen: `parseFacelets` → Fehler in Meldungsbereich; sonst `solve`. Leere Lösung → „Schon gelöst!“.
- Lösung: alle Züge als Notation, aktueller Zug hervorgehoben; Text „Schritt k von n: R' – rechte Seite gegen den Uhrzeigersinn“ (U = obere, R = rechte, F = vordere Seite; 1 = im Uhrzeigersinn, -1 = gegen den Uhrzeigersinn, 2 = halbe Drehung (180°)). - Hinweis über der Lösung: „Halte den Würfel so, wie du ihn eingegeben hast: U oben, F vorne. Drehrichtung jeweils mit Blick auf die Seite.“
